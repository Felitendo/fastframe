fastframe 0.10.0 stops audio from dropping out on a busy Linux machine. The thread that fills the sound card now runs ahead of everything else, as PipeWire's own threads do, so a compile, an analysis or a game on every core no longer leaves gaps in the music. Apps can also count how often the sound card played silence because the app was late.

Upgrade by moving every fastframe crate to the tag:

```toml
fastframe-audio = { git = "https://github.com/crmne/fastframe", tag = "v0.10.0" }
```

No change is required. Solco and Spotifast, the apps that play audio through `fastframe-audio`, get the Linux fix by upgrading. ZapFast, TonePush and the Chat with Work local agent do not use `fastframe-audio`; for them this release changes nothing.

## New

- **Count the gaps the listener hears (`Clock::underruns`).** It counts the times the device played silence because the output's callback came too late, read from the device's own timeline of when each block plays (PipeWire's graph clock, CoreAudio's host time, WASAPI's buffer position), so a callback that is late but still in time does not count, and a pause does not either. It is one relaxed atomic read, cheap enough for every frame or every callback. Solco's audition stress test uses it: a 60 ms stall of the callback reads as one underrun, and with the fix below a fully loaded Linux machine reads none. Backends that report no playback times count none. By @crmne.

## Fixed

- **Audio no longer drops out on a busy Linux machine.** cpal calls the output back from a thread of its own, on PipeWire, PulseAudio and ALSA alike, and leaves it at ordinary priority unless built with its `realtime-dbus` feature. With a 512-frame buffer that thread has about 10 ms each period, and on a loaded machine an ordinary thread can wait longer: in Solco, with its analysis running and one busy process per logical CPU on a 24-thread Ryzen 9 9900X, the callback waited up to 50 ms, PipeWire counted 34 cycles the app missed in a minute, and `Clock::underruns` 12 gaps. The output now asks RTKit, which PipeWire already uses for its own threads, to make that thread real-time (priority 10) on its first callback, or, when that is refused, to raise its nice level. The callback never waits for this: a helper thread makes the D-Bus call. On the same machine and load, the longest wait fell to 10.9 ms, one period, and PipeWire and `Clock::underruns` counted no misses, in that scenario and with a 4 GB memory sweep added. RTKit's `RLIMIT_RTTIME` condition is met by lowering the process's limit to RTKit's maximum (200 ms by default), as PipeWire's clients do. Without RTKit, on a minimal system or in a Flatpak sandbox, or when it refuses, the thread keeps ordinary priority and the outcome is logged once at info level. By @crmne.

  cpal's own `realtime-dbus` feature worked as well on the same load (no gaps, 11.5 ms longest wait), but it links the C libdbus and adds the `dbus` 0.6 and `libdbus-sys` crates, and it covers only cpal's PipeWire and ALSA hosts. This uses `zbus`, already in every app's dependency tree, and covers every Linux host.

- **The documentation of the feeding thread said the callback already ran on PipeWire's or PulseAudio's own thread on Linux.** It ran on cpal's, at ordinary priority. The crate's documentation and README now say what happens. By @crmne.

## Measured

Solco's audition stress test plays an inaudible tone (about -100 dBFS) through `fastframe-audio` while it seeks, starts and pauses every few seconds, and counts the silences in what it played, `Clock::underruns` and the backend's errors. Each scenario ran for a minute.

| Platform | Load | Before: underruns | After: underruns | Longest callback gap, after |
| --- | --- | ---: | ---: | ---: |
| Linux, PipeWire, Ryzen 9 9900X | Solco's analysis | 0 | 0 | 10.9 ms |
| Linux | analysis and 24 busy processes | 12 (PipeWire: 34 missed cycles) | 0 (PipeWire: 0) | 10.7 ms |
| Linux | that and a 4 GB memory sweep | 2 (PipeWire: 2) | 0 (PipeWire: 0) | 10.7 ms |
| macOS 27, M4 Mac mini | analysis, 10 busy processes and a 12 GB sweep that swapped 9.6 GB | 0 | 0 | 11.8 ms |
| Windows 11, Ryzen AI 9 HX 370 | 24 busy processes, and a 16 GB sweep | 0 | 0 | 10.3 ms |

The macOS callback already ran on CoreAudio's real-time thread, and Windows' in MMCSS; this release changes neither. On Windows, Solco's own GPU analysis on the integrated Radeon 890M delayed that MMCSS thread past its period (3 to 5 gaps a minute) until Solco made its inference batches smaller while an audition plays; MMCSS's "Pro Audio" task and a larger buffer did not remove those gaps, so `fastframe-audio` keeps its "Audio" task and the app's buffer.

## Dependencies

- `fastframe-audio` now uses `zbus` 5.19 on Linux, with the `blocking-api` and `async-io` features, as `fastframe-desktop` and `fastframe-text` already do.

## Known limitations

- **Real-time needs RTKit.** Most desktops run it (PipeWire needs it for its own threads). A Flatpak sandbox cannot reach it, and the thread keeps ordinary priority there; the Realtime portal is not used yet.
- **A runaway callback is stopped.** Under real-time scheduling, a callback that ran 200 ms of CPU without waiting would end the app, as it would any PipeWire client. A callback that renders in time never comes near it.
