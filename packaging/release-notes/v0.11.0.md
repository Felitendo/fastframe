fastframe 0.11.0 sends every app's Linux audio straight to the sound server. `fastframe-audio` now plays to PipeWire, or to PulseAudio where PipeWire isn't running, instead of through ALSA's plugins, without the app turning anything on. So every app gets the real-time audio thread from 0.10.0 on an ordinary desktop, not only apps that had enabled a feature.

Upgrade by moving every fastframe crate to the tag:

```toml
fastframe-audio = { git = "https://github.com/crmne/fastframe", tag = "v0.11.0" }
```

**Linux builds now need PipeWire's headers and clang**, for cpal's PipeWire backend: `libpipewire-0.3-dev clang libclang-dev` on Debian and Ubuntu, `pipewire clang` on Arch. Packages need PipeWire 0.3.53 or later, since the app links `libpipewire-0.3.so.0`. No code change is required.

## Changed

- **Linux audio goes to PipeWire or PulseAudio itself (`fastframe-audio`).** cpal's PipeWire and PulseAudio hosts are always built in on Linux, so the default host is PipeWire, then PulseAudio, then ALSA, whichever is running. Before, an app without the `pipewire` or `pulseaudio` feature listed only ALSA devices and played through ALSA's `pipewire`, `pulse` or `default` plugin, which since 0.10.1 keeps ordinary priority. The two features remain, so apps that named them keep building, but they change nothing now. Found by the Spotifast session. By @crmne.
- **The driver's buffer on PulseAudio is 20 ms (`fastframe-audio`).** PulseAudio's own target is about two seconds, which no app means when it asks for the driver's buffer (`Buffer::Driver`, or `Buffer::FixedOnWindows` elsewhere than Windows). PipeWire and every other driver keep their own size. By @crmne.

## Known limitations

- **Mixers show cpal's names for the stream.** cpal's PulseAudio client is called `cpal-pulseaudio-<pid>`, and its PipeWire stream sets no media role, so an app can't yet name its stream or ask for the communication role.
