fastframe 0.12.1 fixes recording and playback in `fastframe-audio`. A mono microphone recorded in stereo on PipeWire no longer has a silent right channel, even after the default microphone changes, and the audio callback no longer allocates memory while playing.

Upgrade by moving every fastframe crate to the tag:

```toml
fastframe-audio = { git = "https://github.com/crmne/fastframe", tag = "v0.12.1" }
```

No code change is required.

## Fixed

- **A mono microphone records in every channel (`Input`).** cpal's PipeWire backend links a stream's channels to the microphone's one by one, without mixing, so a two-channel input on a mono source captured the right channel silent, at half the level. cpal's PipeWire default input also says two channels whatever the source, so the default options hit it too on a mono default microphone. An input now opens at the source's own channel count and gives the app the channels it asked for: a mono source in every channel, many channels averaged down to mono, and otherwise the channels both have, with the rest silent. This happens on the audio thread without allocating. `Capture::configure`, `Input::channels()` and `Maintained::Reopened` give the channels the app gets, as before. With a FLOW 8 microphone on PipeWire, a two-channel input captured -53.9 dBFS on the left and silence on the right before; now both channels carry the same signal, as on the default input. The `capture` example takes `--channels` and shows the loudest sample of each channel. Found by the Spotifast session. By @crmne.
- **An input on the default microphone follows it to a source with other channels (`Input::maintain`).** PipeWire moves a stream on its default input to a new default source itself, at the channels it opened with, so going from a stereo source to a mono microphone would leave the right channel silent again. `maintain()` now reopens such an input at the new source's own channels and returns `Reopened` with `DefaultChanged`. Until the next `maintain()` the capturer gets the new source at the old channels, so keep calling it every second or so, as before. With the `capture` example's new `--watch` mode, switching the default with `pactl set-default-source` from the FLOW 8 microphone to its stereo line input and back reopened the input at 2 channels, then at 1. Inputs opened by id or name, and outputs, carry on as before. By @crmne.
- **The output callback no longer allocates while playing.** It built a small list of blocks to render on every callback; it now walks them without one, and its sample buffer is sized when the stream opens for a fixed buffer, as an input's are. With the driver's buffer it grows once to the first callback's size. A test checks that a callback's work makes no allocation. By @crmne.

## Known limitations

- **Building on Linux needs PipeWire 0.3.53 or later.** cpal's PipeWire backend, always built in on Linux since 0.11.0, builds against libpipewire, and the app links it when it loads. Ubuntu 22.04 has 0.3.48, so it cannot build `fastframe-audio`; Ubuntu 24.04 and Debian 12 are the oldest releases that can.

- **Opening PipeWire's default input can wait up to two seconds.** cpal's PipeWire default input does not say how many channels the source has, so opening it asks PipeWire's PulseAudio server, on the thread that opens and never on the audio thread. That adds about 6 ms (9 ms where 0.12.0 took 3 on the test machine), but a server that does not answer holds the open, and the reopen `maintain()` makes after the default source changes, for up to cpal's two-second timeout. Open inputs off the UI thread, and call their `maintain()` there too. `Input::device_id()` then needs no second asking. Outputs do not wait for it.
