fastframe 0.5.2 keeps the window drawing while settings and history are saved, and logs it when the window freezes. Spotifast's window froze for over ten seconds under disk load, because each save waited on the UI thread for the disk to confirm it. ZapFast saves the same way. The writer Spotifast built to fix it is now in `fastframe-file` for every app.

Upgrade by moving the tag on every fastframe crate:

```toml
fastframe-file = { git = "https://github.com/crmne/fastframe", tag = "v0.5.2" }
fastframe-shell = { git = "https://github.com/crmne/fastframe", tag = "v0.5.2" }
```

Move `fastframe-file` and `fastframe-shell` together: the shell uses `fastframe-file` now, and two copies in one build would miss each other's mark.

An app on `fastframe-shell` that still saves with `fastframe_file::write`, `write_private` or `write_with` on its UI thread now panics there in a debug build (ZapFast's settings, for one). Hand those saves to a `fastframe_file::Writer`. A release build only logs an error and still saves.

## New

- **Saves no longer freeze the window (`fastframe_file::Writer`).** A `Writer` takes the bytes and writes them on a thread of its own, with the same guarantees as `fastframe_file::write`: the old contents or the new ones, never half of either, and on the disk when done. Writes to one file keep their order, and a newer save of a file whose last save has not started yet replaces it, so a burst of saves writes only the newest contents. `flush` waits for everything handed over, for a bounded time, before the app exits or acknowledges a suspend. A failed write is logged and can call back, so the app can write it again later. By @crmne.
- **A save on the UI thread is caught (`fastframe_file::mark_ui_thread`).** `fastframe_shell::Shell::run` marks its thread, and an app without the shell calls it once on the thread that draws the window. After that, `write`, `write_private` and `write_with` on that thread panic in a debug build, so a test catches a save that would freeze the window, and log an error in a release build, which still writes rather than lose the save. By @crmne.
- **Freezes show in the log (`fastframe_shell::StallWatch`).** Run the window's logic and drawing through it, and an update of 250 ms or more logs a warning with how long it took. The first update, which builds fonts and textures, is never reported, and a burst of stalls makes one warning every ten seconds that counts the rest. By @crmne.

The [fastframe-file README](https://github.com/crmne/fastframe/tree/v0.5.2/crates/fastframe-file#saving-from-the-ui-thread) and the [fastframe-shell README](https://github.com/crmne/fastframe/tree/v0.5.2/crates/fastframe-shell#stalls) show them, and the fastframe-power docs now say to flush before acknowledging a suspend or the end of the session.
